# A Curriculum for Tool-Use Agents That Reduces Error Cascades

## Abstract

Tool-use agents built on large language models often fail not on the first tool call but several steps later, when an early mistake — a malformed argument, a misread return value, a wrong tool choice — propagates through subsequent reasoning and compounds into task failure. We call this an *error cascade*. We propose **Staged Tool Curriculum (STC)**, a training and fine-tuning curriculum that orders tool-use practice by *recoverability distance*: the number of downstream steps an error at a given stage typically corrupts before the agent can self-correct. STC begins with single-tool, single-step tasks with immediate ground-truth verification, then introduces multi-tool chains, then noisy/adversarial tool outputs, and finally long-horizon tasks with delayed verification, interleaving explicit self-check and rollback exercises at each stage. We evaluate STC against three baselines — uncurated i.i.d. fine-tuning, difficulty-only curricula, and reward-only RL fine-tuning — on a suite of 420 synthetic and semi-realistic tool-use tasks spanning API orchestration, code execution, and web-browsing-style retrieval. STC reduces cascade failures (task failures traceable to an early, uncorrected error) by 41% relative to the uncurated baseline and 22% relative to the difficulty-only curriculum, while modestly improving raw single-step tool accuracy (+3.1 points). Ablations show that the self-check/rollback stage and the noisy-tool-output stage each contribute independently to cascade reduction, and that ordering matters: reversing the curriculum (hard-to-easy) erases most of the gain.

## 1. Introduction

Tool-use agents — LLMs that call external functions, APIs, code interpreters, or retrieval systems in a loop — are increasingly deployed for tasks that require many sequential, dependent actions. Unlike single-turn generation, tool-use is compounding: each step's output becomes part of the context for the next decision. This creates a distinctive failure mode largely absent from single-turn evaluation: an early, small error (an off-by-one in a query parameter, a misparsed JSON field, a hallucinated tool name) does not simply produce one bad step — it silently changes the "world state" the agent believes it is in, and every subsequent decision is conditioned on that corrupted belief. We call the resulting failure an **error cascade**, and we distinguish it from a *terminal error* (a single fatal mistake with no continuation) and from *independent errors* (unrelated mistakes at different steps).

Standard fine-tuning and RL pipelines for tool-use agents typically optimize end-task success rate on a fixed distribution of tasks, sampled i.i.d. or ordered by naive difficulty (e.g., number of steps). This gives the model little explicit signal about *when* an error occurred versus when it merely *manifested*, and provides no dedicated practice at detecting that the current trajectory has diverged from a valid one. We hypothesize that cascade failures are disproportionately a curriculum problem, not a capability problem: models that can perform each constituent skill (correct tool selection, argument formatting, output parsing, self-verification) in isolation still cascade when these skills are only ever trained jointly on full-length, undifferentiated trajectories.

We propose **Staged Tool Curriculum (STC)**, which orders training data along an explicit axis of *recoverability distance* — a proxy for how many future steps a given class of error is expected to corrupt if uncorrected — rather than raw step count or holistic difficulty. STC has four stages:

1. **Atomic stage**: single tool call, immediate programmatic verification of the call itself (right tool, right arguments, correctly parsed return value).
2. **Chaining stage**: 2–5 tool calls with clean (non-adversarial) outputs, verification of intermediate state at each step.
3. **Noisy-output stage**: same chain lengths, but tool outputs are perturbed (truncated fields, error responses, rate-limit messages, semantically similar but wrong results) to force explicit detection and recovery.
4. **Long-horizon stage**: 6–20 step tasks with only sparse, delayed (end-of-trajectory) verification, requiring the agent to carry forward the self-check habits from stage 3 without step-level supervision.

Each stage is paired with a **self-check/rollback exercise**: after a designated fraction of trajectories, we inject a labeled error and train the model to (a) recognize divergence from expected state and (b) emit a rollback/retry action rather than continuing to build on the corrupted state.

Our contributions are: (1) a formalization of error cascades as distinct from terminal and independent errors, with a measurable metric (Cascade Failure Rate, CFR); (2) the STC curriculum design and training recipe; (3) an evaluation suite of 420 tool-use tasks with instrumented ground truth at every step, enabling cascade attribution; (4) ablations isolating the contribution of ordering, noisy-output exposure, and rollback training.

## 2. Method

### 2.1 Formalizing error cascades

We model a tool-use trajectory as a sequence of (state, action, observation) triples $\tau = (s_0, a_1, o_1, s_1, a_2, o_2, s_2, \dots, s_T)$, where $s_t$ is the agent's *believed* world state after step $t$ and $a_t$ is a tool call. We define the *ground-truth* state sequence $s_t^*$ independently via the task's oracle simulator. A step $t$ is a **primary error** if $s_t$ diverges from $s_t^*$ in a way that affects task-relevant predicates, and it induces a **cascade** if the trajectory fails at the end ($T$) and no later step $t' > t$ both (a) detects the divergence and (b) restores $s_{t'} \approx s_{t'}^*$ or reaches the goal via an alternate valid path.

We report:
- **Task Success Rate (TSR)**: fraction of trajectories reaching the goal state.
- **Cascade Failure Rate (CFR)**: fraction of *failed* trajectories attributable to an uncorrected primary error at least 2 steps before the final step (as opposed to terminal errors on the last 1–2 steps, or independent unrelated errors).
- **Recovery Rate (RR)**: of trajectories with a primary error, the fraction that still reach the goal (self-corrected).

### 2.2 Curriculum stages in detail

**Stage 1 — Atomic.** ~4,000 single-call examples across 30 synthetic tool schemas (REST-style APIs, a Python execution tool, a search tool). Each example has a programmatic checker for tool choice, argument schema validity, and correct parsing of the returned value into the next reasoning step. Training signal: supervised fine-tuning (SFT) on correct traces, plus a binary "was this call and its parsing correct" auxiliary loss.

**Stage 2 — Chaining.** ~6,000 examples, 2–5 dependent calls (e.g., look up a user ID, then fetch that user's orders, then compute a total), clean outputs. We additionally supervise an explicit **state summary** token block after each observation ("what I now know / what I still need"), which is used in later stages as the object the rollback check operates over.

**Stage 3 — Noisy outputs.** Same task family as Stage 2, but 35% of tool outputs are perturbed: truncated JSON, HTTP 429/500-style errors, a field silently renamed, or a plausible-but-wrong value swapped in (e.g., a similar user ID). Ground truth includes whether the current output is corrupted. We inject a **rollback exercise**: at a random perturbed step, the target trajectory is not "continue reasoning" but "flag inconsistency with state summary, re-issue or repair the call, then continue." Loss is applied both to the detection decision and the corrected continuation.

**Stage 4 — Long-horizon.** ~2,500 examples, 6–20 steps, sparse verification (only final goal state is checked, mirroring realistic deployment where step-level oracles don't exist). No new supervision signal is introduced; the aim is to test transfer of the Stage 3 self-check habit under delayed feedback. We use rejection sampling: multiple rollouts per prompt, keep successful ones for SFT, matching standard STaR-style bootstrapping, but we do *not* introduce this until the curriculum has established atomic and chaining competence, to avoid reinforcing lucky-but-unprincipled trajectories.

Stages are trained sequentially (not mixed) on the same base model, each stage initialized from the previous stage's checkpoint, following the ordering above. Total additional SFT compute is modest: 4 stages × 1 epoch each over stage-specific data, using a 7B-parameter open-weight instruction-tuned base model (fine-tuned identically across all conditions to isolate the curriculum variable).

### 2.3 Baselines

- **B1 — Uncurated i.i.d.**: identical total data (atomic + chaining + noisy + long-horizon examples pooled) shuffled and trained in a single pass, no staged ordering, no explicit self-check supervision.
- **B2 — Difficulty-only curriculum**: staged purely by step count (short chains → long chains), without the noisy-output or rollback-specific supervision; clean outputs throughout except in the final stage where noise is introduced without dedicated rollback labels.
- **B3 — Reward-only RL**: base model fine-tuned with outcome-only RL (sparse task-success reward) via rejection sampling over the same task pool, no intermediate supervision or curriculum staging.

All conditions use the same base model, same total number of gradient steps, and the same evaluation suite.

### 2.4 Evaluation suite

420 tasks across three domains, each with an instrumented oracle simulator providing ground-truth state at every step (so CFR/RR are computable, not just TSR):
- **API orchestration** (180 tasks): multi-endpoint CRUD-style workflows against a mocked service layer.
- **Code execution** (120 tasks): tasks requiring a Python tool to compute intermediate values used in later steps.
- **Retrieval/browsing** (120 tasks): a mocked search+fetch tool with distractor pages and occasionally stale/incorrect snippets.

Each domain includes a held-out subset (30%) with tool schemas and task templates unseen during any curriculum stage, to test generalization rather than memorized recovery patterns.

## 3. Results

| Method | TSR (%) | CFR (%) | RR (%) | Single-step tool acc. (%) |
|---|---|---|---|---|
| B1 — Uncurated i.i.d. | 54.2 | 61.0 | 18.4 | 82.1 |
| B2 — Difficulty-only | 58.9 | 46.3 | 27.1 | 83.6 |
| B3 — Reward-only RL | 57.1 | 50.7 | 24.0 | 81.4 |
| **STC (ours)** | **66.8** | **36.0** | **44.9** | **85.2** |

(CFR is measured as a percentage of failed trajectories; lower is better. RR is measured as percentage of trajectories with a primary error that still succeed; higher is better.)

STC improves TSR by 12.6 points over B1 and 7.9 points over B2, driven substantially by CFR reduction (a 41% relative drop vs. B1, 22% relative vs. B2) and more than doubled recovery rate relative to B1. Notably, single-step tool accuracy — the metric standard training pipelines optimize for — improves only modestly (+3.1 points over B1), confirming that the bulk of STC's benefit comes from *recovery behavior* rather than fewer primary errors. On the held-out (unseen schema) subset, STC's CFR advantage narrows but persists (STC 41.2% vs. B2 51.8%), indicating the self-check behavior transfers beyond memorized patterns rather than collapsing to it.

**Ablations** (removing one component from STC, evaluated on the full suite):

| Variant | TSR (%) | CFR (%) |
|---|---|---|
| STC full | 66.8 | 36.0 |
| − Stage 3 (skip noisy-output stage) | 61.0 | 45.9 |
| − rollback loss (state summary kept, no injected-error training) | 62.4 | 44.1 |
| − staged ordering (same data, shuffled) | 58.1 | 49.5 |
| Reversed order (hard→easy) | 55.7 | 58.2 |

Removing the noisy-output stage or the rollback-specific loss each recovers roughly half of the gap to B2, showing the two are complementary rather than redundant: exposure to corrupted outputs alone is insufficient without an explicit trained response to them. Reversing the curriculum order performs *worse* than the shuffled-data ablation, suggesting that presenting long-horizon, sparse-feedback tasks before atomic competence is established actively teaches the model to paper over errors rather than detect them — consistent with our hypothesis that curriculum order, not just data composition, is doing the work.

**Qualitative failure analysis.** Manual inspection of 50 B1 cascade failures found the modal pattern was silent continuation: the agent's state summary (when reconstructed post hoc) showed an obviously stale or contradictory belief (e.g., referencing a user ID that the last tool call had explicitly rejected) that was never revisited. In STC trajectories with a primary error, the most common recovery pattern was an explicit re-issued call with a comment noting the prior output looked inconsistent, matching the Stage 3 training signal directly.

## 4. Conclusion

Error cascades — not raw per-step tool accuracy — are a major and separately addressable source of tool-use agent failure. Curricula that order training by recoverability distance, and that explicitly train detection-and-rollback behavior under noisy tool outputs before extending to long-horizon sparse-feedback tasks, substantially reduce cascade failures without requiring more total data than standard pipelines. The ordering itself matters, not merely the presence of hard examples: naive difficulty curricula and reward-only RL both leave most of the cascade-reduction benefit on the table, and inverting the order is actively harmful. We see two natural extensions: (1) applying STC-style staging within RL fine-tuning objectives directly (rather than SFT-then-nothing), and (2) using the learned self-check state-summary representation itself as a lightweight runtime monitor for deployed agents, independent of retraining. Limitations include reliance on synthetic/mocked tool environments with programmatic oracles, which may understate the diversity of real-world tool failure modes (rate limits with backoff semantics, partial writes, non-idempotent side effects); validating CFR reduction on production-scale, real-API agent logs is the priority next step.
