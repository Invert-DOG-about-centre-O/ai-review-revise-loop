# Lessons for writing a better first draft

- **Run multiple seeds from the start for any claim about a specific location, threshold, or boundary.** A single-seed "clean crossover at X" claim is the single most predictable thing reviewers will attack — all four round-1 reviewers independently re-ran the code with different seeds and broke the headline number. If the paper's core finding is "X happens at/between specific value(s)," budget for a seed sweep (10+ seeds) in the first draft, not as a round-2 patch. Report the finding as a distribution (mode/range) plus a variance estimate, not a point.

- **Never derive RNG seeds from `hash()` of a string, or any other process-randomized/non-frozen source.** Python's `hash()` on strings is randomized per-process by default, so seeding via something like `base_seed*K + hash(name)%N` makes every rerun silently produce different data — in this paper it caused all four round-1 reviewers to get different p-values than the paper claimed, none of which matched each other either, burning a full review round on a bug that should have been caught by the author simply rerunning their own script twice. Use a fixed integer mapping (explicit dict or index) for any per-condition seed offset, and rerun your own experiment end-to-end at least twice before submission to confirm bit-identical results.

- **When running a statistical test, fix the null hypothesis independent of the observed data.** Choosing the null's reference set (e.g. "uniform over the three widths we happened to observe") after seeing which values occurred is a post-hoc null, and reviewers will flag it as an easier bar than it looks. Test against a null defined in advance (e.g. uniform over the full grid actually searched), or report both and be explicit about which is the conservative one.

- **Pre-register the sample size itself, not just the null hypothesis and stopping rule — run a power calculation before collecting data, and if the design is structurally underpowered, redesign it rather than caveat it.** In one paper, the confirmatory test's sample size was capped by definition (only seeds where a crossover existed at all qualified, yielding n=7 vs n=4), giving a minimum detectable effect so large (rank-biserial ~0.74) that the test could only ever catch a huge effect. Every reviewer in every one of 4 rounds flagged this, and it was never fixable post-hoc because the fix — a different test design or more seeds/conditions to enlarge the eligible n — had to be chosen before round 1. A pre-registered null (see above) prevents a post-hoc-easy test; a pre-registered power calculation prevents a foreseeably-underpowered one. Do both at design time.

- **Report a null/non-significant result together with its power analysis, not instead of it, and never use strong rejection language ("decisive," "rules out," "retires") for a weak or non-significant result.** "Not significant" and "no effect" are different claims, and p=1.00 on n=15 is evidence of an underpowered test, not evidence against the hypothesis. One paper's round 3 draft called a p=1.00 Fisher's test result "decisive enough to retire that explanation" — all four reviewers independently objected, and the fix (adopted in the next round) was softening to "consistent with X rather than a formal rejection of it." Write that hedged version in the first draft: compute effect size, CI, and minimum detectable effect, and match your verbs to what the numbers actually support.

- **If you extend a sample size because an initial test came back non-significant, that is sequential testing / optional stopping, and it must be disclosed and corrected for — not reported as if it were one uninterrupted test.** Peeking at n=15, seeing p>0.05, then extending to n=50 on the same seeds plus new ones and reporting the n=50 p-value as the headline result inflates the true false-positive rate even when every individual number is honestly computed and fully reproducible. Either pre-register the final n before looking, or explicitly frame a second look as confirmatory with alpha-spending / its own stated significance threshold. This is subtle enough that it can survive multiple rounds of otherwise-thorough statistical review before a reviewer catches it — decide the stopping rule before running the first test, not after seeing the first result.

- **When a paper accumulates many exploratory follow-up tests across revisions (mechanism checks, sensitivity sweeps, ablations, baseline comparisons), track the total test count and address multiple comparisons**, rather than letting each new follow-up test be judged significant or not in isolation. A revision history with 6+ tests run across rounds, several only nominally significant (p just under 0.05), reads very differently once a reviewer adds them up — plan for this from round 1 by either pre-specifying a small confirmatory test set or explicitly correcting/discussing the multiplicity when more tests accumulate.

- **Every statistic quoted in the abstract or main text must be persisted in the artifact/result file that computes it, not just hand-derivable by a reviewer from raw per-seed data — and every rounded figure must be checked against the unrounded value in that file.** If prose cites a specific p-value, accuracy, or other number, make sure the corresponding JSON/results file actually contains that computed value under a discoverable key, and that any rounding is honest (e.g. don't write "~0.94" when the file says 0.9248 — reviewers will recompute it from the raw results and catch the gap, as happened independently to two reviewers in one paper's round 3). An unsaved or over-rounded statistic is a reproducibility/trust gap even when the underlying number turns out to be qualitatively correct.

- **Verify mechanism hypotheses directly instead of asserting plausibility, and when you do run the verifying ablation, check it doesn't contradict other evidence already in the paper.** If you speculate a cause for observed noise/variance (e.g. "probably binning artifacts," "probably dimensionality," "probably too-small validation set"), don't just state it — run the check that would confirm or falsify it, and afterward re-read the rest of the paper for pieces of evidence that cut the other way. In one paper, a late-round ablation supporting "dimensionality drives the effect" was added without reconciling it against an earlier real-dataset result that was higher-dimensional but showed the effect *less* reliably — a direct tension a reviewer caught in the final round because no one had cross-checked the new ablation against the old data point. A plausible-sounding but unverified (or internally inconsistent) mechanism claim is exactly the kind of thing that costs a full extra cycle.

- **When reporting a "before vs. after" comparison (an intervention, a fix, a calibration step), verify both numbers come from the literal same trained model/run, not from two separately-retrained populations that merely share a nominal seed label.** A script that calls the RNG-seeding function once per seed and then trains many conditions sequentially (multiple widths × multiple settings) does NOT give each individual condition an independently reproducible model — the RNG state at the point a given condition is reached depends on everything trained before it in that loop. A later follow-up script that reseeds immediately before training just that one condition in isolation produces a *different* model, so splicing its "after" number onto the original script's "before" number silently compares two different sets of weights. Always seed immediately before each individually-reported unit of training, and if two numbers in the same table row come from different scripts/files, explicitly check they refer to the same trained artifact before pairing them.

- **Apply the same verification rigor to every quantified claim in the abstract, not just the one under active reviewer scrutiny.** In one paper's final round, an easily-falsifiable claim ("hidden≥32 is overconfident in all 10 seeds") sat unchecked in the abstract for two full revision rounds — while a different headline claim received binomial tests, bootstraps, and dual nulls — and turned out to be false by the paper's own results file (two seeds reverted to underconfident at large widths). Before finalizing, grep/recompute every absolute quantifier ("all," "every," "always," "never") in the abstract and discussion against the actual results file.

- **Small held-out splits (a few hundred examples) make point estimates and post-hoc fits (temperature scaling, threshold/crossover locations) noisy enough to change qualitative conclusions.** State this early and quantify it (bootstrap variance) rather than only noting it qualitatively in Limitations — reviewers consistently asked for exactly this and rewarded it when eventually provided.

- **Full, exact reproducibility (code + raw logs/result JSONs that regenerate every reported number) is consistently and heavily rewarded by reviewers, across every round.** It has been the single most-praised property across papers in this series, and papers that start from these lessons (fixed seeding, pre-registered nulls, power analyses, mechanism verification already in v1) now reliably clear round 1 with zero reproducibility complaints. Always ship runnable code alongside raw output files, and make sure every number quoted in prose/tables can be regenerated from them — but also make sure the regeneration is deterministic (see the `hash()`-seeding lesson above); reproducible-but-wrong is worse than no reproducibility claim at all.

- **Honest, substantive walk-backs of overprecise claims (rather than defending them or patching cosmetically) are recognized and rewarded by reviewers as "the correct epistemic move."** When a review round shows a headline claim doesn't hold up, downgrade the claim's precision explicitly in the text (state what changed and why) rather than quietly softening the language or arguing the original framing was fine.

- **If the title or abstract makes a generality claim ("generalizes across datasets," "holds across architectures"), decide at round 1 which causal axes reviewers will ask about, and run independent manipulations of each of them up front — don't let the paper discover its own confounds one at a time, one review round apiece.** A title promising cross-dataset generality but backed by one real dataset plus variants of one synthetic generator family, on one architecture, was flagged by every reviewer in every round (16/16 reviews) and never resolved because fixing it meant adding a second dataset/architecture, a round-1 decision. Worse, when reviewers asked "is it difficulty?" (round 2) and the author added a difficulty ablation, the *next* round's reviewers immediately asked "then is it dimensionality?" — each fix satisfied that round but revealed the next confound, costing a full round per axis. Before round 1, list the 2-3 most obvious alternative explanations a skeptical reviewer would propose for your effect, and run a manipulation isolating each one in the first draft, rather than tightening scope language or chasing confounds reactively.

- **Single-dataset, single-architecture (or single-framework/optimizer) empirical studies plateau around a 5-7 rating even when extremely well-executed and statistically rigorous.** Reviewers consistently cap novelty/generality scores for narrow scope regardless of how much statistical rigor is added on top, and broad claims in the abstract/title will repeatedly be flagged as reading more general than a single-setup result can license. Either scope the claims' language tightly to what was actually tested from the first draft, or budget for a second dataset/architecture/implementation if a higher ceiling is wanted.

- **Not all reviewer criticisms are equally fixable within a revision cycle.** Methodology/implementation bugs (bad seeding, unverified mechanism claims, over-rounded numbers, overclaiming language) are typically fixed for real within one round once flagged. Design-time decisions — final scope/generalizability, the statistical testing/stopping plan, and sample-size power (not just the null definition) — tend to just get re-flagged or hedged with "future work" language across every remaining round, because the fix requires a decision made before round 1, not a patch after the fact. When starting a new paper, spend extra first-draft effort specifically on these categories: pick the final scope, the full statistical testing/stopping plan, and a power calculation for the sample size, all up front — since they are the ones later rounds cannot cheaply repair.
