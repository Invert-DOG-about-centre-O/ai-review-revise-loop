# Lessons for writing a better first draft

- **Run multiple seeds from the start for any claim about a specific location, threshold, or boundary.** A single-seed "clean crossover at X" claim is the single most predictable thing reviewers will attack — all four round-1 reviewers independently re-ran the code with different seeds and broke the headline number. If the paper's core finding is "X happens at/between specific value(s)," budget for a seed sweep (10+ seeds) in the first draft, not as a round-2 patch. Report the finding as a distribution (mode/range) plus a variance estimate, not a point.

- **When running a statistical test, fix the null hypothesis independent of the observed data.** Choosing the null's reference set (e.g. "uniform over the three widths we happened to observe") after seeing which values occurred is a post-hoc null, and reviewers will flag it as an easier bar than it looks. Test against a null defined in advance (e.g. uniform over the full grid actually searched), or report both and be explicit about which is the conservative one.

- **Verify mechanism hypotheses directly instead of asserting plausibility.** If you speculate a cause for observed noise/variance (e.g. "probably binning artifacts" or "probably too-small validation set"), don't just state it — run the check that would confirm or falsify it (e.g. bootstrap-resample the fixed test set / fixed model and measure the effect directly). A plausible-sounding but unverified mechanism claim is exactly the kind of thing that gets corrected in a later round, costing a full cycle. It's fine to be wrong about the mechanism in an early draft — it isn't fine to state an unverified mechanism as if it were established.

- **When reporting a "before vs. after" comparison (an intervention, a fix, a calibration step), verify both numbers come from the literal same trained model/run, not from two separately-retrained populations that merely share a nominal seed label.** This was the most serious rigor gap in this paper's final round: a script that calls the RNG-seeding function once per seed and then trains many conditions sequentially (multiple widths × multiple settings) does NOT give each individual condition an independently reproducible model — the RNG state at the point a given condition is reached depends on everything trained before it in that loop. A later follow-up script that reseeds immediately before training just that one condition in isolation produces a *different* model, so splicing its "after" number onto the original script's "before" number silently compares two different sets of weights. Always seed immediately before each individually-reported unit of training, and if two numbers in the same table row come from different scripts/files, explicitly check they refer to the same trained artifact before pairing them.

- **Apply the same verification rigor to every quantified claim in the abstract, not just the one under active reviewer scrutiny.** In this paper's final round, an easily-falsifiable claim ("hidden≥32 is overconfident in all 10 seeds") sat unchecked in the abstract for two full revision rounds — while the crossover claim next to it received binomial tests, bootstraps, and dual nulls — and turned out to be false by the paper's own results file (two seeds reverted to underconfident at large widths). Before finalizing, grep/recompute every absolute quantifier ("all," "every," "always," "never") in the abstract and discussion against the actual results file.

- **Small held-out splits (a few hundred examples) make point estimates and post-hoc fits (temperature scaling, threshold/crossover locations) noisy enough to change qualitative conclusions.** State this early and quantify it (bootstrap variance) rather than only noting it qualitatively in Limitations — reviewers consistently asked for exactly this and rewarded it when eventually provided.

- **Full, exact reproducibility (code + raw logs/result JSONs that regenerate every reported number) is consistently and heavily rewarded by reviewers, across every round.** It was the single most-praised property of this paper in every review. Always ship runnable code alongside raw output files, and make sure every number quoted in prose/tables can be regenerated from them.

- **Honest, substantive walk-backs of overprecise claims (rather than defending them or patching cosmetically) are recognized and rewarded by reviewers as "the correct epistemic move."** When a review round shows a headline claim doesn't hold up, downgrade the claim's precision explicitly in the text (state what changed and why) rather than quietly softening the language or arguing the original framing was fine.

- **Single-dataset, single-architecture empirical studies plateau around a 5-7 rating even when extremely well-executed and rigorously verified.** Reviewers consistently cap novelty/generality scores for narrow scope regardless of how much statistical rigor is added on top, and broad claims in the abstract/title ("capacity-agnostic calibration advice is unsafe") will repeatedly be flagged as reading more general than a single-dataset/single-architecture result can license. Either scope the claims' language tightly to what was actually tested from the first draft, or budget for a second dataset/architecture if a higher ceiling is wanted.
