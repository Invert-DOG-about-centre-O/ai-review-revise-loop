# Skills / lessons for writing better first drafts

- Before framing a result as a "finding," check whether it follows directly from the algebra/construction of your own method, or could be explained by an obvious confounding variable in your own setup (e.g., a discretization/functional-form choice, or a covariate like set size that differs between the two things you're comparing). If so, either (a) don't present it as a standalone empirical discovery, or (b) proactively run the cheap confound-controlled ablation in the first draft, not only after a reviewer asks. A recurring, expensive pattern: a headline "method A vs. method B" difference measured at matched nominal parameters (e.g., matched alpha) turns out to be substantially explained by the two methods landing at different set sizes/scales — always ask "matched on what?" and test the alternative matching before claiming the difference is intrinsic to the thing you want credit for. A related shape: if two things you're comparing are mathematically guaranteed to induce the same partition/ranking under your chosen operationalization (e.g., an "exact-match" clusterer makes your semantic-clustering method identical in mechanism to your simpler baseline, or a correction term that depends only on one shared statistic can never invert a pairwise ranking at low sample size), say so explicitly and up front — a near-tie or exact tie you can prove is definitional is a weaker finding than an empirical surprise, and a paper that owns this in the method section (rather than letting a reviewer point it out) reads as more rigorous, not less ambitious. This generalizes cleanly: whenever you see p=nan or a zero-variance paired difference in your own results, that's usually a signal of a definitional tie, not a data problem — track down and state the mechanism rather than reporting the null result unexplained.
- When presenting several interventions/conditions as points on one comparable spectrum or ranking, check that each is a like-for-like manipulation before writing the headline ranking. If one condition mechanically changes an axis the others don't (e.g., swapping an entire agent for a different agent class, rather than adding a policy layer on top of the same underlying agents), decompose it (e.g., report the per-agent/per-component breakdown) in the first draft, not after a reviewer asks — and be honest in the abstract, not just in a buried results paragraph, about how much of the headline pooled effect is compositional versus a genuine behavioral change.
- Every summary statistic in the abstract must be a number you can point to in the results body, not a loose paraphrase. Compute the actual range/ratio across conditions and either report the range or the correct aggregate — don't round a spread of effects (e.g., 2.5x–8.5x) into one punchy headline figure (e.g., "quadruples") that doesn't match any single reported value. This applies to plain counts and tallies too, not just ratios: if the abstract states a total number of sensitivity cells/conditions/checks, recompute it by literally adding up the sub-sweeps described in the method section before submitting — a paper was flagged for an abstract claiming "21 sensitivity cells" when the described sweeps only summed to 12, a discrepancy a reviewer catches by simple addition.
- Any p-value reported as a strict bound (e.g., "p < 1e-41") must actually satisfy that inequality against the number in your own artifact — don't derive the bound by truncating an exact value's mantissa to 1 (e.g., rounding 2.79e-41 down to "p<1e-41" is false; the correct bound is "p<1e-40" or, better, report "p≈2.8×10⁻⁴¹"). This is a distinct, mechanical check separate from ordinary arithmetic recomputation: for any exponent-style claim, verify the direction of the inequality, not just the order of magnitude. Reviewers who are already re-running your code will independently recompute exact p-values and catch every instance of this, and it reads as a systematic overstatement pattern (not a one-off typo) if it appears more than once — prefer "≈" notation over ad hoc "<" bounds unless you've explicitly checked each one. Relatedly: if your design produces astronomically extreme p-values (e.g., p<10⁻⁵³) purely because your per-cell sample size is very large on a mechanically-expected, deterministic effect, say so explicitly in the text ("this reflects sample size, not subtlety") and point the reader to a more informative statistic (a power analysis, an effect size) rather than letting the extreme p-value stand as if it were evidence of a subtle or hard-won result — reviewers read unflagged extreme p-values on textbook-expected effects as a rigor-signaling overreach even when the number itself is correct.
- When a headline effect is a discontinuity/threshold/phase-transition claim, test it at finer resolution than your main sweep grid before submitting — a coarse grid cannot distinguish a true jump from a fast multi-step decline, and reviewers will ask for exactly this check.
- Avoid post-hoc, unjustified cutoffs used to classify results into categories (e.g., "a drop >0.03 counts as a narrow band"). Either use a threshold-free characterization (slope, derivative, AUC of the curve) or report a sensitivity analysis across a reasonable range of thresholds from the start, and be explicit about which conclusions are threshold-sensitive.
- When you run a series of ablations across revisions, check that you're not only ever varying one axis of the setup while leaving other obviously-relevant axes completely untested through every round. This applies at two levels: reviewers will flag an entire untested axis (e.g., only the human/behavioral-model side varied, never the base classifier/dataset), but once every axis has at least one ablation, they will then flag *insufficient diversity within* an axis you did technically cover — e.g., testing robustness to "network structure" with only a single random graph topology (one Erdős–Rényi draw), or testing robustness to a distributional assumption with only one alternative family, is treated as a narrower claim than it sounds. Budget first-draft effort toward covering a couple of structurally different instances per axis you claim to have stress-tested (e.g., two qualitatively different alternative distribution shapes, not one), not just one. This applies with particular force to *null/negative results about a mechanism* (e.g., "targeting doesn't beat blind/uniform application"): such a finding is a property of the one specific mechanism instantiation you tested (e.g., a uniform-random intervention), not evidence about targeting in general, until you've tried at least one qualitatively different instantiation (e.g., a biased/structured intervention) — one paper's "targeting confers no advantage" claim, true under a uniform-random mechanism, reversed substantially once a boundary/structure-biased version of the same intervention was tested, changing the paper's practical conclusion. Flag mechanism-specific null results as such explicitly in the first draft rather than stating them as general negative results. When a reviewer's follow-up question can be answered by re-analyzing data you already collected (e.g., fitting a cross-condition regression over cells from a prior ablation) rather than running a new simulation, do the cheap re-analysis first — it's fast to produce, trivial for the reviewer to re-verify (no new artifact to rerun), and still counts as a substantive, responsive answer.
- If your central phenomenon has a known general mathematical explanation, explicitly connect it to that existing theory/prior work up front, in the first draft — don't present a textbook-known effect (e.g., a classical finite-sample estimator bias, a known correction formula) with framing that could be read as claiming the *existence* of the effect as your novelty. State plainly and early that the base phenomenon is known/expected, and locate your actual contribution precisely (e.g., "the known effect's *magnitude at this specific, previously-unquantified parameter regime*," not the effect itself) — otherwise reviewers will spend multiple rounds probing whether you're claiming more novelty than a well-executed quantification study actually has, even when every number in the paper is correct and honestly reported.
- More rounds of technically excellent, honestly-reported ablations do not guarantee a monotonically increasing review score. Across several papers now, the rating has sat flat (or even dipped a point before recovering) for the final 2-4 rounds even though every concrete reviewer request was fixed each round: once the easy methodological critiques (missing significance tests, missing ablations, unverified thresholds, missing artifacts, seed-count mismatches, incorrect p-value bounds) are resolved, reviewers shift to scrutinizing the core contribution's novelty/significance, related-work depth, and whether the paper's own honesty is shrinking its contribution. One failure shape: a paper launches with two co-equal headline contributions, and rigorous stress-testing across rounds demotes one of them (sign-flips at low seed count turn out to be noise, or the effect is shown to be hyperparameter/topology-dependent) — leaving, by the final round, only one "robust, load-bearing" claim and one "illustrative, not calibrated" claim. A second shape (papers that explicitly disclaim novelty and frame themselves as "an evaluation harness, not a new algorithm," or as "quantifying a textbook-known effect in a new regime"): the score stays capped regardless of added rigor, because the ceiling is set by contribution type, not execution quality. A third shape, seen when a toy/synthetic setup stands in for a real target domain: reviewers keep flagging the same "this is a proxy, not the real mechanism" gap every round even as every *other* requested fix lands cleanly — added rigor within the proxy domain (more seeds, richer variants, power analyses, noise-interaction models) demonstrably strengthens the proxy-domain claims but cannot, by construction, close the proxy-vs-real gap, so it stops moving the score once that's the dominant remaining critique, and the paper's own most novel finding (e.g., a correction "overshoot" effect) gets explicitly downgraded by reviewers to "an existence proof, not a calibrated threshold" for lack of a real-world anchor on the one parameter that would calibrate it. A fourth shape (a fully self-consistent simulation with essentially no correctness weaknesses left to find): the score can plateau one point below the ceiling for the paper's whole remaining lifetime simply because the sole recurring weakness — a single, coarse external calibration point — is real but structurally unfixable within the paper's scope (no access to more human-subject data), so reviewers keep naming it without it ever being resolvable in-paper. A fifth shape: once every reviewer-requested experiment has already landed in an earlier round, a revision that responds to review with prose reframing alone (tightening the abstract's argument, restructuring the introduction, adding cross-references to related work already cited) — with zero new experiments, data, or numbers — gets explicitly called out by the reviewer as "a rewording pass, not a substantive revision," and the score does not move even one point, up or down. Where possible, figure out in the first draft which of your candidate claims is actually going to survive heavy stress-testing (run the cheap high-seed-count sensitivity checks *before* writing the abstract), and if your design is inherently a proxy for a domain you can't directly test (no internet, no production access, no real dataset), decide up front how you'll anchor it to that domain (see below) rather than spending three rounds proving the proxy is internally solid while the external-validity gap goes untouched. Corollary: once you notice a revision round has no new experiment planned, that is itself a signal — spend the round attempting the cheapest still-open reviewer request (even a partial/proxy answer, see below) rather than polishing prose that reviewers have not asked you to polish.
- Related-work sections that give one-sentence characterizations of each cited paper (or stay in the 5-8 total citation range) get flagged as shallow, and this critique tends to recur across multiple review rounds unaddressed if not fixed early — engage substantively with at least the most central 2-3 citations (what they measured, what they didn't test, how your parameters relate to any quantity they report), and expand citation breadth to cover the wider space of related models/approaches, not just the one or two papers you calibrated against.
- Don't assert a novelty claim ("we are not aware of prior work that...") without substantiating it against the broader literature in the same section. An unsupported novelty assertion gets flagged as thin even in a late-round, otherwise well-defended paper — either cite enough related work to make the claim credible or soften it to a scoped statement about what you did test. A strong first-draft alternative to a bare novelty claim: cite a *concrete existing pipeline* that already reaches for the fix/idea you're formalizing (e.g., "system X already applies an ad hoc version of this correction, without quantifying it") — this converts an assertion about the literature's absence into evidence of the literature's need, and is both more convincing and cheaper to defend under review than a negative existence claim.
- If your method is a simulation/proxy standing in for a real-world system or domain, find at least one empirical anchor point from cited literature — or a real-world spot-check, even partial — to calibrate against, even approximately. Leaving the mapping from simulation parameter/regime to the real-world target entirely untested through every revision is a recurring, unresolved weakness reviewers keep raising across multiple papers in this series. This applies even inside a fully synthetic setting with no external data available: if a central mechanism (e.g., a regulatory detection trigger, or an assumed noise/error rate for a step you can't run directly) assumes access to ground-truth information no real-world actor would have, or sweeps a plausible-sounding but literally unanchored parameter range (e.g., a clustering-error rate ε∈{0,0.05,0.1,0.2} with no citation for what real systems exhibit), that gap gets flagged every single round until a first-draft proxy/realistic-information variant is tested. It also applies when a hard environment constraint (e.g., a sandboxed machine with no internet access) makes running the real-domain experiment literally impossible: in that case the cheapest available anchor is a *numeric* one — pull the actual reported effect sizes/AUROCs/gaps/error-rates from the papers you're already citing (or from adjacent, easily-citable benchmark numbers, e.g., published accuracy of the class of model your simulated noise term stands in for) and state explicitly in the text how your proxy's parameter or effect size compares in magnitude. A paper that never quotes "our synthetic gap/parameter is X, the real-domain literature reports Y" leaves reviewers to ask this as a question every round instead of getting an answer; citing published numbers costs nothing (no internet needed, just reading your own reference list closely, or citing one more widely-known benchmark number) and it's usually a cheap addition since the rest of the writeup already exists. This lesson has been in this file before and been violated again since: a paper explicitly said, in its own limitations section across three consecutive rounds, that it had "no empirical citation pinning down realistic [parameter]" for its most novel finding, and never attempted the cheap literature-anchor version of the fix (e.g., citing a published NLI/entailment-accuracy benchmark as a rough proxy for the clustering-error rate it was sweeping) even though the fix requires no new experiment, just reading — treat any self-acknowledged "no anchor" limitation as an action item to resolve with a citation search in the very next revision, not a permanent disclosure to keep repeating. Note also that even a well-executed single anchor (one interpolated number checked against one human-subject study) tends to get flagged as "coarse" every round it remains the *only* anchor — if a second, independent real-world number is available from a different cited study, add it, since reviewers evaluate anchor *count and diversity*, not just anchor presence. This has now recurred across a paper that used only a qualitative (directional, not fitted) anchor to a real-world dataset for its entire multi-round lifetime: reviewers named the unfitted anchor as a live weakness in every single round, including the final one, even though every other requested fix (numerical errors, missing sensitivity analyses, mechanism-generality checks) was resolved and the score plateaued at one point below the ceiling — reinforcing that a purely qualitative/directional anchor, however honestly disclosed, does not fully satisfy this lesson; attempt at least a rough numeric fit or range estimate, not just a "same sign" comparison, wherever the cited data permits it.
- Ship deterministic, self-contained, fast-running code alongside every numeric claim in the paper, and double-check before each submission that every artifact/log file path named in the text actually exists in the submitted directory — including new log/results files introduced by a revision's new experiment script, not just the original set. A paper was flagged for listing a `_v2` log file in its "Artifacts" line that had never actually been written to disk, an easy miss when a new script is added mid-series and the artifacts list is updated by copy-paste rather than by checking `ls` against the claim. Full exact reproducibility (a reviewer can rerun your script and match your numbers to the last reported digit) has been consistently rewarded across every review round of every paper in this series — reviewers explicitly rerun the full pipeline each round, so it's cheap to provide and materially increases reviewer trust, and any single missing or non-reproducing number stands out sharply against that reviewer's baseline expectation of exact fidelity. If seeds are derived from strings/tuples via hashing, never use a language's built-in general-purpose hash function for this unless you've confirmed it's stable across processes — e.g., Python's `hash()` on strings/tuples is randomized per-process by default (PYTHONHASHSEED), so code that looks deterministic (fixed base seed + `hash(params)`) can silently produce a different run every single execution despite the paper claiming exact reproducibility. Use a purpose-built stable hash (e.g., `hashlib.sha256` on an encoded string) for any seed-derivation step, and verify determinism by actually diffing outputs from two fresh-process reruns, not just by reading the code and assuming a fixed base seed is sufficient. Numeric results (means, p-values, AUROCs) are not the only claims reviewers reproduce: machine-dependent facts like wall-clock runtime are also treated as claims to verify, and get burned just as hard when wrong — one paper stated "runtime: 28.4s" from a single early run and never re-measured it before final submission; an independent reviewer rerun took ~5-8x longer, and the discrepancy was flagged as a correctness issue on par with a wrong numeric result, not waved off as "just hardware." Before final submission, freshly re-run and re-time everything you report a wall-clock number for (or explicitly caveat it as machine/BLAS-dependent and avoid stating it as a bare fact), and treat "a number I measured once, early, and never re-verified" as a generic risk category, not one confined to statistical results.
- Recompute every ratio/"roughly Nx" comparison stated in prose directly from the numbers you report elsewhere in the same paper before submitting, especially after a late revision changes an upstream number. Reviewers who are already verifying your code will also hand-check your arithmetic and tallies, and a stale or miscalculated figure is a concrete, easily-caught overclaim that undermines an otherwise rigor-focused paper. Also reconcile the same figure if it's quoted more than once (e.g., abstract vs. main text) against slightly different reference numbers — pick one comparison basis and use it consistently. This includes any headline number derived by interpolation (e.g., "find where curve A returns to curve B's baseline value") — actually perform the interpolation against your own logged sweep values before writing the number down; a paper's round-1 headline figure (η≈0.47, "~30% relative accuracy cost") turned out not to match a straightforward linear interpolation of its own results.json (correct value: η≈0.35, ~22% cost), a discrepancy the reviewer caught simply by redoing the interpolation from the same artifact the paper cited.
- Beyond arithmetic, check that prose *characterizations* of a result (e.g., "never significant," "no effect," "robust across conditions") match the actual number and p-value in your own results table, not just a plausible-sounding summary of it. A revision once described a table cell as "never significant, even reversing sign" when the same table's own paired-t p-value for that cell was p=0.005 (Bonferroni p=0.019) — i.e., a statistically significant reversal, and a materially more interesting finding than the prose claimed. Reviewers cross-check narrative sentences against your own tables just as readily as they check them against external facts, so add a pass before submission where you re-read every qualitative claim in the text next to the specific cell/row it's summarizing. When a later round's more targeted follow-up ablation contradicts or narrows a blanket claim made in an earlier round (e.g., "no detectable effect" becomes "a small, real effect at the single most extreme condition tested, absent everywhere else"), explicitly revise/retract the earlier sentence in the text rather than only appending a new caveat beside it — reviewers have explicitly praised this as "the kind of update a reviewer wants to see, not just added caveats," and it reads as stronger evidence of rigor than defending the original broader claim would.
- If a sweep or ablation turns up one anomalous/outlier cell or an unexpected sign flip relative to the rest of the grid, don't just flag it as unexplained and move on, and don't assume it's noise (or assume it's real) without checking — rerun that specific cell/slice at a matched, higher seed count before concluding either way. This is a recurring, two-sided pattern: a paper that ran most of its sensitivity grids at a lower seed count than its main sweep (e.g., 10-15 seeds vs. 30) got asked whether every "surprising" cell was sampling noise; when it reran, most flips did indeed turn out to be noise, but one flip reran as a genuine, statistically decisive reversal (p<0.0001) that changed the paper's qualitative story in that regime. The lesson is not "sign flips are always noise" — it's that any ablation run at reduced seed count relative to your main sweep is not yet a trustworthy claim in either direction, and matching seed counts across all sensitivity checks in the first draft avoids an entire extra review round spent just re-running at higher N. This applies with special force to whichever finding turns out to be your most novel/consequential one. In practice, reviewers may not always flag a lower-seed-count ablation explicitly (a paper can score well while its sensitivity sweeps run at 20 seeds/cell vs. a 30-seed main grid) — but treat the mismatch as latent risk rather than evidence the practice is safe, since whether it gets caught seems to depend on whether any specific cell result looks surprising enough to invite scrutiny.
- When you claim a small-sample effect is "seed-stable," "not noise," or "reliably significant," back it with a formal paired statistical test (paired t-test, Wilcoxon signed-rank) in the same draft you make the claim — don't rely on informal evidence and wait for a reviewer to ask for the formal version. If a reviewer (or you, anticipating one) notices the effect is only *sometimes* significant at your default sample size, the strongest response is an actual power analysis — sweep n across a few values, run multiple independent replicates at each, and report the fraction reaching significance at each n. This converts "seed-sensitive, might be fragile" into a concrete, defensible statement ("reliably significant, 5/5 replicates, at n≈1200; at our default n=300 it's real but not always significant, which is the expected behavior of a modest true effect at that sample size") — a materially stronger and more honest answer than either overselling the default-n result or shrugging at the inconsistency, and it also gives readers the practically useful number (how much data is actually needed) instead of just an abstract significance claim. When a test has a known small-sample floor, report that floor honestly alongside the more appropriate test rather than omitting the unfavorable result.
- If a diagnostic or mechanism check (e.g., a "why does this happen" measurement like a frozen/discarded-update fraction) is used in the text to explain a headline numeric result, make sure that diagnostic is computed on the *exact same run/grid* that produced the headline number, not a separate, smaller, or differently-parameterized sweep that merely overlaps in spirit. A reviewer will explicitly check whether the explanatory diagnostic and the effect it explains come from the same data, and quoting a mechanism percentage from a different experiment than the effect size it's meant to justify is flagged as a reproducibility/rigor gap even when both numbers are individually correct and reproducible.
- A plausible-sounding post-hoc mechanistic explanation for a surprising result (especially a counterintuitive one, like a noisier/weaker-information version of a mechanism outperforming the "ideal" version, or two error sources partially canceling rather than compounding) should either be tested directly with an added diagnostic, or explicitly labeled as untested speculation in the same sentence — don't let confident prose about "why" a result happened stand in for evidence that the proposed mechanism is actually what's driving it. Reviewers will accept the effect size as established (if reproducible) while separately flagging the causal story behind it as unverified, so keep those two claims visibly distinct in the writing.
- When a paper reports many individual significance tests across a large sensitivity grid (e.g., 15-20+ per-cell p-values across several stress-test dimensions), address multiple-comparisons correction explicitly — either apply one, or state briefly why it's not needed (e.g., effect sizes are large/consistent enough that correction wouldn't change conclusions). Leaving a large multi-cell battery of p-values entirely unaddressed on this point gets flagged even in an otherwise well-regarded late-round paper.
- When a reviewer (or your own read of the results) calls an effect size "small," "modest," or "practically marginal," first check whether the estimate is an artifact of a narrow or arbitrary design choice you made when constructing the experiment (e.g., a hand-picked set of only 3-4 variants/conditions/perturbations meant to illustrate a mechanism, not to bound it) before accepting the "modest effect" framing as final. Testing a broader or richer version of that same choice — more variants, more diverse instances, a wider parameter range — can reveal your original number was a conservative lower bound rather than the true effect size, which is a substantially stronger rebuttal than defending or hedging the original modest number. Explicitly framing a follow-up experiment this way ("if this generalizes the wrong way, it hurts our story, so it's a real test, not padding") also helps the reviewer trust the result wasn't cherry-picked.
- If an ablation/robustness axis turns out to be structurally broken (e.g., a nuisance variable creates label imbalance so severe that a whole metric is undefined for some conditions no matter how you resample), attempt exactly one dedicated rescue in the round after it's first flagged — e.g., resample more draws, or sweep the one knob (training budget, sample size, hyperparameter) most likely to fix it. If that rescue attempt shows the imbalance is structural (moving the knob in one direction fixes one sub-condition while breaking an adjacent one, rather than fixing all of them at once), say so plainly and stop investing further rounds trying to rescue it — report it as an intrinsic limitation of the task/setup design instead of re-attempting fixes each round. Reviewers explicitly downgrade papers less for having one clearly-diagnosed-as-unfixable ablation than for spending multiple rounds re-poking at the same broken axis without ever concluding it's unfixable; by the third round of a still-broken ablation, reviewers themselves may suggest cutting it, which is a signal you should have reached that conclusion first. Better still: when designing the first draft, sanity-check whether any planned difficulty/nuisance axis scales so steeply that no single operating point can give every level of that axis balanced positive/negative labels — catching this before the first draft avoids the wasted rounds entirely.
- When a low-dimensional summary/predictor for a multi-parameter effect is proposed (e.g., "the ratio of two rates predicts where an effect flips sign better than either rate alone"), test it against the obvious alternative summaries (difference, product, each raw parameter alone) in the same round you propose it, not just the one you expect to win — reviewers will ask for exactly this comparison, and running it yourself first, including reporting where your favored summary still falls short (e.g., residual scale-dependence at fixed ratio), reads as more credible than presenting only the winning candidate.
- When you disclose an environment constraint that blocks the ideal experiment (e.g., no network access, no model-hub download, a broken TLS chain), diagnose it precisely enough to state what *is* and *isn't* reachable (e.g., "general HTTPS to other hosts works; only the model-hub's specific CA chain fails validation") rather than a vague "no internet." A precise diagnosis both makes the disclosed limitation more credible to a skeptical reviewer (it reads as an actually-investigated blocker, not a convenient excuse) and helps you and future revisions correctly identify which workarounds are actually available (e.g., other HTTPS-reachable data sources are still usable, only that one hub is blocked).
- If your headline "cost"/"effect"/"harm" number depends on how you operationalize an abstract outcome (e.g., "accuracy" measured as a threshold pass/fail vs. a continuous correlation-with-ground-truth), test at least one alternative reasonable operationalization in the first draft, not only after a reviewer asks. The magnitude can differ substantially between definitions (one paper's mitigation "cost" was ~15-22% under two threshold-based accuracy definitions but ~24-35% under a continuous correlation-based one) without either being wrong — report the range across definitions and state plainly which stakeholder/use-case each definition corresponds to, rather than presenting a single number as if it were definition-independent.
- When a table or summary sentence aggregates a statistic across a condition you are also varying elsewhere in the paper (e.g., one shared "Accuracy" column reported once per row of a table whose rows are actually cross-cut by two separate sweep axes, like a noise-distribution choice and a correlation parameter), check whether the aggregated/shared number actually holds for *all* the sub-conditions it's presented next to, not just the one you happened to check. A single column or claim that silently averages over, or is only true for, one sub-condition (while the text implies it applies uniformly) reads as misleading even when every underlying number is individually correct and reproducible — split the column/claim per sub-condition instead of presenting one merged summary.
- Before submitting any revision, cross-check every parameter setting/row named in the prose or tables against the actual script that is cited as producing it — not just "does a script with this name exist and run," but "does it contain and execute every specific configuration (every slope, every W value, every named condition) the text quotes numbers for." A paper added a new robustness table citing three parameterizations of an alternative functional family (e.g., three slope values) and a supporting script by name, but the script as submitted only implemented and ran one of the three; the other two rows' numbers were not reproducible from any code in the repo. This is a more severe, harder-to-excuse failure than an arithmetic slip — reviewers who rerun your code (which they consistently do in this series) treat a cited-but-unexecuted result as presenting fabricated numbers as real ones, and it cost a full point of rating even though every *other* number in the paper was exactly reproducible. The fix, once caught, must be to actually add the missing configuration(s) to the script and rerun end-to-end (and say so explicitly, e.g. "closing the reproducibility gap flagged last round") — a promise to have run it, or a plausible-sounding number without the corresponding code, does not recover trust; only a rerun-and-verified table does. Generalize this into a pre-submission checklist step for every revision that adds a new table or new cited numbers: for each cell, locate the exact script + config that produced it and re-execute that specific config, not just the script as a whole.
